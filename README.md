# LLMOS Project — Directory Guide

One rule decides where everything below lives:

**Is this actively maintained, or is it archived history?**
Then, if actively maintained: **is it hand-authored, or generated by a tool?**

That's the whole taxonomy. Five folders, no deeper nesting than necessary.

```
llmos_project/
├── kernel/          hand-maintained behavioral spec — edit these directly
├── llmos_toolkit/     the Python package — code, not prose
├── state/            tool-generated files — never hand-edit, safe to delete and regenerate
├── projects/          things built USING the kernel+toolkit
└── reference/         archived history — read for ideas, don't build on directly
```

## kernel/

The canonical, currently-in-force behavioral spec. Three files:
- `HCF_LLMOS_Kernel_v1.3.6-C.md` — the methodology itself
- `SEMANTIC_DRIFT_POLICY.md` — companion policy for meaning-drift during edits
- `UNIFIED_BEHAVIORAL_OUTPUT_PROTOCOL_v2.md` — reasoning-process and output-shape rules

These are the only files in this whole tree you should be routinely
hand-editing. Everything else either generates from these, references
them, or is history that led to them.

## llmos_toolkit/

The `llmos_toolkit` Python package as-is — `core/` (registry, plugin
loader, security, CLI), `plugins/` (growth_budget, drift_check,
claim_flag, token_audit, adaptive_drift_logger, sync, example_hello),
and `hooks/` (git pre-commit template). Its own `README.md` inside this
folder has the full command reference — not duplicated here.

**The folder must be named exactly `llmos_toolkit`** — `python -m
llmos_toolkit` resolves that name to this directory, and the plugins
import `from llmos_toolkit.core.registry import registry` directly.
Renaming it breaks both. (Caught this the hard way building this
structure — see verification note at the bottom of this file.)

Run it by setting `PYTHONPATH` to this file's directory (`llmos_project/`,
the one containing `llmos_toolkit/`), from wherever you want generated
state to land — `state/` is the intended working directory:
```
cd state
PYTHONPATH=/path/to/llmos_project python3 -m llmos_toolkit --list-commands
```

## state/

Everything the toolkit generates when you run it — ledgers, pins, drift
baselines. Currently seeded with `growth_ledger.jsonl` carrying real
history from the kernel's consolidation pass. Everything else
(`.drift_state.json`, `kernel_pins.json`, `token_ledger.jsonl`,
`drift_rules.json`, `drift_audit.jsonl`) gets created here the first
time you run the relevant command — **run toolkit commands from this
directory** (or point them at files using paths into `../kernel/`) so
generated state lands here instead of scattering wherever a command
happened to be invoked from.

This whole folder is regenerable. Safe to delete if you want a clean
slate — nothing here is a source of truth, only a record of runs.
`handoff_rag.db` specifically regenerates in seconds via `rag-index` —
never worth treating as precious.

**Verification note:** the toolkit was actually run from this structure
before packaging — `pin-kernel` and `verify-kernel` were tested against
`kernel/HCF_LLMOS_Kernel_v1.3.6-C.md` from `state/`, both passed, and
`kernel_pins.json` landed here correctly. Not just a proposed layout —
confirmed working as described.

## projects/

Actual work-product that *uses* the kernel/toolkit — not part of the
LLMOS infrastructure itself.
- `depolarize/` — the anti-bias/de-escalation prompt, its requirements
  ledger, maintenance toolkit, and changelog
- `threat_response/` — the draft corrective-action reference guide

Future unrelated projects go here as new sibling folders, each self-
contained. This is the folder that grows over time; the other four
should stay close to their current size.

## reference/

Archived, not actively maintained. Two subfolders:

- **`llmos_architecture_history/`** — superseded kernel/adapter
  versions, the original design-spec docs now superseded by the actual
  toolkit code, and — inside
  `original_llmos_tangent_no_working_artifact/` — the full 17-file
  LLMOS bundle from the original ChatGPT tangent that never produced a
  working browser extension. Kept for provenance, not as something to
  build on.
- **`pilot_and_research/`** — the shared-substrate pilot design, the
  mathematical-gateway research conversation, process manuals, the
  boundary report, cognitive-state-intervention notes, and the (unrun)
  pilot harness code. Real, carefully-designed material — just nothing
  here is currently being executed or depended on by anything active.

Nothing in `reference/` needs a decision. It sits here until something
concrete in `projects/` or `kernel/` actually needs to draw on it —
same treatment as any other logged-not-built open item.

## What's deliberately NOT in this tree

`AI-Coordination-070526.zip` was found in the upload directory during
this reorganization but never discussed in the conversation that
produced this structure, and contains a file that appears to hold real
credentials (`DO-NOT-SYNC/activepieces-secrets.md`). It was excluded
entirely, not filed into `reference/`. If it belongs in this project,
it needs a deliberate decision to include it — and the secrets file
specifically should never be zipped into anything that leaves your
machine.
