# LLMOS Submission Contract — v0.1 (DRAFT, NOT IMPLEMENTED)

*Originally conceived as a conflict resolution management system; became this epistemic-discipline kernel and toolkit for LLM work through a real redirection -- see `docs/PROJECT_PRIORITIES.md`'s Origin and Scope Evolution section.*

**Status: design candidate. No transport implements this yet.** Drafted
jointly (Claude + ChatGPT relay, 2026-08-21/22) after finding that the
existing multi-instance quarantine pattern (`propose-observation` /
`approve-pending` / `reject-pending`) has only ever been operated by
one instance on another's behalf via human relay -- never invoked
directly by a second, independently-running instance. This is the
minimal semantic contract that any real transport (Vercel endpoint,
MCP tool, localhost, GitHub Issues, continued human relay) would need
to implement identically, so the first working transport doesn't
accidentally become the protocol itself.

## Why this exists before any endpoint

Building `/observations` on the deployed Vercel relay first, without
freezing this contract, would let Vercel's specific request/response
shape define the semantics by accident. Any second transport (say, an
MCP tool) would then either have to match Vercel's incidental choices
or fork the semantics. Freeze the contract first; let every transport
implement the same thing.

## Submission

```
SUBMISSION
  submission_id     -- generated by the interface, not the participant
  participant_id    -- which instance/session is submitting (e.g. "chatgpt-relay-2026-08-22")
  session_id        -- groups submissions from one conversation/run
  parent_id         -- optional, links to a prior submission this responds to or supersedes
  type              -- observation | action | response | recalibration_request
  payload           -- the actual content, shape depends on type
  provenance        -- what this is grounded in (mirrors --source on propose-observation)
  epistemic_status  -- VERIFIED | INFERRED | ASSUMED | UNKNOWN (A3's existing taxonomy, reused not reinvented)
  created_at        -- ISO 8601, set by the interface on receipt
```

## Lifecycle

```
SUBMISSION
    |
PENDING  ---------------------------- same shape as pending_observations.jsonl today
    |
    v (human/governance gate -- same quarantine boundary already in use)
    |
ACCEPTED | REJECTED | QUARANTINED
    |
    v (ACCEPTED only)
canonical LLMOS ledger (state/growth_ledger.jsonl or its successor)
```

No submission reaches the canonical ledger without passing through
PENDING and an explicit human decision. This is not a new rule --
it's the existing `propose-observation`/`approve-pending` boundary,
generalized from "one instance operating it on another's behalf" to
"any instance operating it directly."

## Explicit non-goals for v0.1

- **No participant holds persistence credentials.** The interface
  (whatever it turns out to be) holds whatever's needed to write to
  the canonical ledger. Participants only ever submit and read their
  own submission's status.
- **No participant gets standing write access to the canonical
  ledger**, regardless of transport. ACCEPTED is not the same as
  "the participant wrote it" -- a human or governance process
  performs the actual promotion.
- **This does not define a transport.** Vercel, MCP, localhost, or
  continued human relay are all equally valid implementations of this
  same contract. Building one is not choosing it as canonical.

## Open questions, not resolved by this draft

- Where does `epistemic_status` get assigned -- by the submitting
  participant, or independently by the interface? (Current
  `propose-observation` lets the proposer state it; the interface
  doesn't currently second-guess it before human review.)
- What happens to a `type: recalibration_request` submission --
  there's no existing analog to `drift-log-confirm` operating on
  demand from a remote participant.
- Whether `parent_id` chains need their own integrity check (does a
  submission's parent have to already be ACCEPTED, or can it chain
  off something still PENDING?).

These are worth resolving before implementation, not during it.
